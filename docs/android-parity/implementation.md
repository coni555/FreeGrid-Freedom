# 开发顺序与交给 AI 的任务书

更新：2026-10-27。用户已定安卓一次完整上线；下述为内部实施与验收顺序，任何阶段完成都不自动触发对外发布。本次仅更新规格，尚未实现任何安卓版新功能。完整产品目标见 [规格](product-spec.md)，逐项现状见 [差距清单](android-gaps.md)。

## 范围与启动条件

当前可直接蒸馏的完整目标为 iOS 2.0＋2.1。保留 Flutter，按数据、计算、功能、平台接入拆工作；没有必要因为 Swift 与 Dart 不同就整仓推倒。原先分批发布免费核心的建议作废。

渠道、支付与 2.2 / 2.3 首发范围是开工前需收口的产品决定，详见 [范围更新](v2.1-update.md) 和后面的待定表。规划、合成案例和只读审计可以继续；本次请求不擅自扩成完整安卓版开发，也不先接入某个支付渠道再倒逼产品决定。

## 第一阶段：建立可靠的数据底座

目标：旧用户能安全升级；当前 iOS 数据不能被悄悄读残或写残。

- 从 Android main 最新提交创建独立工作区；先保存并审理现有四个未提交改动，不替别的任务提交它们。
- 保留 Flutter、包名、正式签名和已有系统适配；验证目前依赖，不默认升级框架或引入新依赖。
- 明确持久化选择；实现区分首次安装/损坏/升级的启动状态、原数据快照、原子写入/恢复。
- 扩展模型和 codec，覆盖数据字典；保留业务 UUID；把整份快照重建引起的字段丢失封住。
- 对尚未开放的 Pro 编辑能力，决定“完整保留只读”或“明确阻止不能无损承接的导入”；不得静默降级。

完成门槛：A33–A43 中相关案例通过；合成当前备份导入→普通记账→再导出字段仍完整；旧本地库迁移幂等；错误注入后重启核对原账不变。当前 schema 4 补丁不能作为格式真源。

## 第二阶段：统一计算

目标：同一账本、偏好、权益和时间，两端财务结果一致。

- 统一 Snapshot/FreedomState；有效支出起点、日均大额、被动周期、计入金额、日历计划。
- 核心计算依赖传入 now/calendar，而非各页面自行读时钟；UI/预览/模拟/趋势共用。
- 将 [计算案例](fixtures/calculation-cases.json) 接入 Dart 测试。可给 iOS 增加读取同一 JSON 的测试适配器，但不为了迁移复制整套 UI。
- 根据 iOS 已有测试补写超400天固定支出、短月、退款、无效数据与夏令时边界。

完成门槛：A01–A20、A26、A30、A32 的对应案例一致。按原始数值、状态、显示与格子分别比较；本包提供的期望是起点，不是覆盖全部场景的证明。

## 第三阶段：免费核心完整操作链

目标：在内部构建中走通所有免费操作链，为同一个完整发布版打底。

- 免费固定支出：创建→修改→到期处理→明细→撤销→待处理→删除。
- 支出/收入/编辑、日均显示、资产总开关、被动周期、明细搜索、模拟同步新口径。
- 按功能拆 `dashboard_shell.dart`；先沿输入→保存→显示路径拆分，不为架构增加空壳层。
- 使用说明、页面讲解与实际能力同步。首次空账本替代种子账本。

完成门槛：相关 A21–A49 通过；flutter analyze/test 通过；构建 APK；在已有 Android 模拟器和真机上体验，并验证旧APK覆盖升级。无需为追赶创建新模拟器。

本阶段不是独立上架版本，也不意味着取消安卓 Pro 或把所有权益免费。数据结构和状态必须从一开始承载完整目标。

## 第四阶段：2.1 功能闭环

- P14：中文/English资源与格式化；默认分类和自动备注只翻译展示。文案资源边界从前面阶段开始，最后集中查漏。
- P12 / P16：三组九项、免费收入/结余、无限 Pro 目标；用相同财务摘要验证目标进度，不实现旧 GAP 预测方案。
- P15：七张小卡、今日长条与每个目标卡；默认/全部移除/重排/收起都持久化，普通布局全部免费。
- 为原有五项 Pro 权益补齐失效和恢复行为，再接第六项目标及小组件权限。内部测试可注入权益状态；正式构建不能以调试开关代替购买链。
- 将 D07 的偏好与账本备份分开，不在 UI 暗示目标已被备份。更新说明、指引和九项自检解释一起完成。

完成门槛：A53–A71、A80 及原有 Pro 案例通过；用户更改语言、资产排除、支出、目标、权益后，首页/自检/目标都刷新到同一结果。

## 第五阶段：平台接入与权益闭环

开始收费相关开发前解决下列待定项；独立的卡片展示/引导/视觉可按前面已确定规则进行。

| 待定项 | 为什么需要决定 | 不影响哪些工作 |
|---|---|---|
| Android 分发渠道与支付方式 | 当前 APK 直发没有已实现的收款/权益链 | 数据模型、算法、免费核心、只读保真 |
| Pro 权益在 Android 的开放方式 | 免费给、后续开放、购买解锁会影响入口和失效行为 | 全量规格与测试输入可以先保存 |
| 跨端购买/体验是否互认 | 涉及身份和凭证；当前无账号，不可从备份自动解锁 | 账本跨端导入 |
| 是否允许为购买增加网络能力 | 当前 Android 约束为无网络权限 | 纯本地流程 |
| 新 2.2 / 2.3 哪些纳入首个完整版 | 原完整发布承诺基于旧两版路线，不能自行扩缩 | 当前 2.1 规格、原型与案例 |
| 小组件的 Android 尺寸、锁屏与刷新方式 | 不同平台形态不能由 WidgetKit 配置推断 | 摘要契约与投影测试 |
| Android 自动备份是否纳入及方式 | iCloud 不是通用跨端服务，当前仍有离线约束 | 本地导入导出与数据保护 |

本轮把待定项落为明确边界，不要求用户逐条回答才能完成规划。下一次启动业务开发时按 HANDOFF 先确定渠道/收费和首发范围；技术试验只用合成数据，不能提前写成上线承诺。

- 依据 P17 / D08 实现 Android 系统小组件：天数、看板两项选择、目标选择；桌面展示和锁屏支持分别验收，不用 Flutter 页面里的普通 Widget 冒充系统桌面小组件。
- 真实主账本一个真源，发布可重建的摘要；处理 30 天投影、午夜切日、过期提示、更新失败、目标删除及权益变化。支付尚未闭环不可宣称 Pro 可购买。
- 完成门槛：A72–A77；旧用户保留正式包名/签名升级；渠道选择确定后补购买、取消、恢复、退款、离线和免费体验的实际验证。需要新增依赖或网络能力时按项目约束先定具体方案。

完成后统一验收子账户、分类、贷款、自由卡、目标、小组件和权益变更。iOS 的 StoreKit 商品加载、恢复购买、原生评价、SwiftData 实现不逐句移植；Android 用选定渠道和本地技术实现同一产品结果。

## 第六阶段：性能、视觉和一次完整发布验收

- 以 A78–A79 验证隐藏页、输入响应、保存后更新和大账本搜索；缓存失效错误必须先修，不靠展示旧数据换流畅。
- 使用合成演示账本对照信息层级、排版、颜色、字重、动效和状态；不把旧真实账本截图作为素材。
- 使用现有 Android 模拟器；用户实际体验后明确同意才合并新功能。
- 合并前整合最新 main，验证受影响规则；只提交本任务文件。发布 APK 仍需明确的发布授权。
- 将最终确认纳入的 2.2 / 2.3 项补齐规格与验收；完整范围未达标不按“免费先发”绕过。
- 正式覆盖升级保留原包名与签名；密钥不打印、不提交；不可把 debug 签名当正式签名回退。
- 删除本任务已合并的分支、工作区和临时构建产物，保留必要测试证据和构建缓存；不清理其他任务或用户账本。

## 给实现 AI 的任务书模板

> 你在 FreeGrid Android 项目工作。先读该项目 AGENTS/HANDOFF，再读 iOS 仓库 `docs/android-parity/README.md`、本次相关规则和案例。
>
> 本次范围：〔内部阶段、P/G/A编号〕。对外一次完整上线；本阶段不是单独发布授权。源码基线：〔iOS提交〕、〔Android提交+已明确接纳的补丁〕。先核对基线差异，不自动把后续路线图算入本次。
>
> 按输入→保存→显示实现完整操作链。保留旧数据、正式签名、包名、离线隐私约束和已有适配；不删除未归属本任务的改动。需要新增依赖、收费/联网或新的用户可见规则时，先列出实质性影响。
>
> 将指定合成案例接成真实测试；遇到原说明、用户决定和源码冲突，报告具体位置与两种行为，不能凭猜测抹平。每完成一个模块更新差距状态、测试证据和 HANDOFF。
>
> 交付：代码、相关测试结果、合成账本截图/操作证据、仍未覆盖的情况。先让用户在该分支实际体验，明确同意后再合并。不要用“构建通过”代替功能完成。

## 后续双端同步

以后每次业务规则变更，同时改相应 P 规则、A 案例及 JSON 期望；记录来源提交。更新 G 条目的状态需附测试/体验证据，不能因新增了同名页面就改为“完成”。

建议增设一个轻量变更表：日期、规则编号、前后行为、iOS提交、Android提交、验证结果。只在真正发生双端规则变化时写，避免另造冗余项目管理系统。进度仍写各自 HANDOFF。

不要把本包变成第二份长期漂移的代码。固定规则可以保留概括，算法细节和边界通过共享案例与源码引用检查；重大改动重新生成 baseline，不将上一次扫描结论永远当现状。
